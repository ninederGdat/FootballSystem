# ================================================================

# FootballSystem - Project Rules

# ================================================================

## 1. PROJECT IDENTITY

This repository is FootballSystem.

FootballSystem is a football data application that synchronizes
football data from Fotmob and exposes the processed data through
a .NET backend and frontend application.

The backend is a C#/.NET project.

Primary backend technologies:

- C#
- .NET
- ASP.NET Core
- Entity Framework Core
- PostgreSQL
- Supabase
- Quartz.NET
- Playwright
- Fotmob external data

Backend implementation MUST use C# unless the user explicitly
requests another language.

# ================================================================

# 2. ABSOLUTE LANGUAGE RULE

# ================================================================

DO NOT generate Python for backend implementation.

If the user asks to create:

- Repository
- Service
- Controller
- API
- Entity
- DTO
- Mapper
- Resolver
- Sync service
- Migration-related code
- Test

the implementation MUST be C# unless explicitly requested otherwise.

If Python appears in an example from another context, do not
interpret that example as the project's implementation language.

# ================================================================

# 3. CODEBASE-FIRST DEVELOPMENT

# ================================================================

Before implementing a non-trivial request, inspect the existing
codebase.

Do NOT immediately generate generic code from the task description.

The preferred workflow is:

User request
↓
Inspect codebase
↓
Find similar implementation
↓
Inspect dependencies
↓
Understand data flow
↓
Understand business rules
↓
Implement
↓
Compare with existing patterns

# ================================================================

# 4. PATTERN REUSE

# ================================================================

Existing project code is the primary source of truth for:

- architecture

- DTO patterns
- entity patterns
- exception handling
- logging
- async programming
- CancellationToken usage

Do not replace an existing project convention with a generic

# ================================================================

# 5. ARCHITECTURE

# ================================================================

Respect the existing application architecture.

The normal dependency direction is:

API / Controller
↓
Service
↓
Repository
↓
Database / External data source

Do not bypass layers without a concrete reason.

Do not introduce a new architecture simply because it is common
in generic examples.

# ================================================================

# 6. REPOSITORY DEVELOPMENT

# ================================================================

When asked to create or modify a Repository:

1. Search for existing Repository implementations.
2. Find the closest Repository by responsibility.
3. Inspect its interface.
4. Inspect its implementation.
5. Inspect related Entity classes.
6. Inspect DbContext usage.
7. Inspect existing query patterns.
8. Inspect async and CancellationToken usage.
9. Follow the established pattern.

Do not invent a new Repository abstraction.

Do not introduce a generic repository if the project does not
already use one.

# ================================================================

# 7. SERVICE DEVELOPMENT

# ================================================================

When asked to create or modify a Service:

1. Search for similar Services.
2. Inspect their constructor dependencies.
3. Inspect their Repository dependencies.
4. Inspect related DTOs.
5. Inspect related Entities.
6. Inspect exception handling.
7. Inspect logging.
8. Inspect business logic.
9. Follow the established Service pattern.

The Service should use the project's existing Repository and DTO
patterns.

Do not create an independent architecture.

# ================================================================

# 8. API / CONTROLLER DEVELOPMENT

# ================================================================

When asked to create an endpoint:

1. Find similar endpoints.
2. Inspect route naming.
3. Inspect HTTP method conventions.
4. Inspect request DTOs.
5. Inspect response DTOs.
6. Inspect pagination/filter behavior.
7. Inspect error handling.
8. Follow the existing controller/API pattern.

Do not invent a different API contract unless explicitly requested.

# ================================================================

# 9. ENTITY / DTO RULES

# ================================================================

Before creating an Entity or DTO:

- search for related models
- inspect existing naming conventions
- inspect property naming
- inspect nullable reference conventions
- inspect mapping conventions

Do not duplicate an existing model.

Do not create a new DTO when an existing DTO already represents
the required response unless there is a clear reason.

# ================================================================

# 10. DATABASE RULES

# ================================================================

The project uses PostgreSQL.

The project uses Entity Framework Core for database access.

Follow the existing:

- DbContext
- Entity configuration
- relationship configuration
- migration
- query
- indexing
- constraint

patterns.

Do not introduce another ORM.

Do not modify schema casually.

When database structure changes, consider:

- Entity
- EF configuration
- migration
- Repository queries
- Service behavior
- API behavior

# ================================================================

# 11. ASYNC / CANCELLATION TOKEN

# ================================================================

The project uses asynchronous operations.

Preserve async/await patterns.

When an existing method accepts CancellationToken:

- preserve it
- propagate it
- pass it to downstream async operations

Do not remove CancellationToken simply to make an implementation
shorter.

# ================================================================

# 12. EXCEPTION HANDLING

# ================================================================

Before creating a new exception:

1. Search for existing exception types.
2. Determine whether an existing exception can be reused.
3. Follow the existing exception naming convention.
4. Follow existing API error handling.

Do not create duplicate exception classes unnecessarily.

# ================================================================

# 13. LOGGING

# ================================================================

Follow the existing logging pattern.

Before adding logging:

- inspect nearby implementations
- use the project's existing ILogger conventions
- use structured logging where the existing code does so

Do not introduce a different logging framework.

# ================================================================

# 14. EXTERNAL DATA / FOTMOB

# ================================================================

Fotmob is an important external data source.

When modifying synchronization logic:

- inspect existing Raw models
- inspect Clean models
- inspect mappers
- inspect resolvers
- inspect sync services
- inspect repositories
- inspect existing data flow

Do not assume that external API data is complete.

Do not change synchronization behavior without examining how
the data flows through the existing pipeline.

# ================================================================

# 15. TRANSFER DOMAIN

# ================================================================

Transfer-related logic is an existing business domain.

Relevant concepts include:

- Transfer
- TransferStatus
- transfer_status
- current
- loaned
- transferred
- Transfer History
- transfer date
- period_start
- period_end

When modifying transfer-related logic:

1. Inspect the existing transfer implementation.
2. Inspect TransferStatusResolver.
3. Inspect Player transfer_status handling.
4. Inspect Transfer synchronization.
5. Inspect Player synchronization.
6. Preserve existing business rules.

Do not infer transfer state solely from the current squad response
if the existing architecture uses transfer history.

# ================================================================

# 16. BUSINESS LOGIC HAS PRIORITY

# ================================================================

Do not replace project-specific business logic with generic
implementation patterns.

For example:

If an existing resolver determines a player's transfer status,
do not replace it with a simplistic:

    if player exists in squad -> current
    else -> transferred

unless the user explicitly requests that behavior.

# ================================================================

# 17. MINIMAL CHANGE

# ================================================================

Prefer the smallest correct change.

Do not modify unrelated files.

Do not perform opportunistic refactoring.

Do not:

- rename unrelated classes
- reorganize folders
- rewrite working services
- replace architecture
- introduce unnecessary abstractions
- change unrelated business logic

# ================================================================

# 18. DEPENDENCY AWARENESS

# ================================================================

Before modifying a class, determine who uses it.

For example:

Repository change
↓
Interface
↓
Service
↓
Controller
↓
DTO / API response

When appropriate, inspect both upstream and downstream dependencies
before changing a public method signature.

# ================================================================

# 19. WHEN CONTEXT IS INSUFFICIENT

# ================================================================

If the required implementation cannot be determined from the
available context:

DO NOT invent missing code.

Instead:

1. State what information is missing.
2. Identify the file or implementation that should be inspected.
3. Ask for that context only when necessary.

Accuracy is more important than producing code immediately.
